# 2026-09-25 — Архитектура решения и план работ

Статус: **предложение**, решает лид. Основано на PDF задачи, README датасета и разборе данных ([data.md](../data.md)).

## Контекст

- Входы: скорость двух тележек (10 Гц, в км/ч) и позиция контроллера (20 Гц). GNSS есть только в первые секунды.
- Баллы: скорость — 30, положение — 35, устойчивость — 20, реальное время — 15. Положение сравнивают по x, y, z и 3D-расстоянию.
- На чистых участках скорость колёс почти идеально совпадает с GNSS. Трудности — пропуски входов (до 73 с), проскальзывание, выбросы, пачки и масштаб колеса, свой у каждого трамвая.
- Все прогоны — одна линия около 7,5 км с петлями на концах. Перепад высот — 35 м.
- Без IMU курс взять неоткуда. Интегрирование скорости в x, y без карты разваливается на первом повороте.

## Решение

1. **Одномерный фильтр вдоль пути.** EKF на состоянии `[s, v, d]`: дистанция вдоль маршрута, скорость и «возмущающее» ускорение (уклон, ошибка модели, случайное блуждание). Опционально — масштаб колёс `k`.
2. **Модель тяги и торможения как предсказание.** `a = f(cmd, v) − сопротивление(v) + d`:
   - тяга — постоянный момент до базовой скорости, затем постоянная мощность, уровень — от позиции контроллера;
   - торможение — сила, пропорциональная тормозной позиции;
   - сопротивление — формула Дэвиса `A + B·v + C·v²`.

   Параметры и поправочную таблицу `a(cmd, v)` калибруем офлайн по GNSS обучающих прогонов. Так задача разрешает: «таблично-аппроксимирующая» или «гибридная» модель, офлайн-калибровка.
3. **Колёса как измерение, с защитой от плохих данных.**
   - Гейтинг по невязке (χ²).
   - Физический предел ускорения по сцеплению.
   - Согласованность передней и задней тележек.
   - Признаки из PDF: резкий рост скорости колёс без модельного ускорения, большой момент при малом ускорении, отрицательное рассогласование при торможении.

   Подозрительное измерение отбрасываем или сильно увеличиваем его шум, фильтр идёт по модели. Когда данные снова в норме, доверие к ним возвращается плавно. Флаг проскальзывания публикуем в диагностику: это прямо даёт баллы по критерию 3.
4. **Положение — по карте линии.** Офлайн по GNSS обучающих прогонов строим карту: замкнутый маршрут «путь туда → петля → путь обратно → петля» с параметром `s`, а также lat, lon и высотой. Онлайн x, y, z = карта(`s`), курс берём по касательной. Стартовую `s` определяет GNSS первых секунд: проекция на карту плюс направление по смещению между точками. PDF прямо допускает такое представление: «координаты вдоль траектории из карты pathgraph», «дистанция вдоль пути и проекция на ближайший участок».
5. **Реализация — Python, rclpy, ament_python, без внешних зависимостей в ноде.** Фильтр маленький (3–4 состояния), требования к реальному времени мягкие: ≤ 100 мс, ≥ 10 Гц, ≤ 2 ядер, ≤ 0,5 ГБ. Numpy в ноде не используем, чтобы `colcon build` и запуск гарантированно работали без интернета на чистом образе. Если профилирование покажет проблему — переносим горячий путь на C++.

## Альтернативы

- **Интегрировать скорость в x, y без карты.** Курса нет, поэтому на поворотах ошибка в сотни метров.
- **Чистая одометрия колёс.** Разваливается на пропусках и проскальзывании, а это 20 баллов плюс точность.
- **Модель ML «чёрный ящик».** Организаторы явно ждут математическую модель, её надо объяснять на питче. ML допустим только как поправка к физической модели.
- **C++ с первого дня.** Надёжнее по времени отклика, но медленнее в разработке, а до дедлайна меньше трёх дней.
