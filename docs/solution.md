# Решение: резервная одометрия трамвая по модели

Документ для формы сдачи: разделы совпадают с её полями (см. [форму](context/2026-09-25-submission-form.md)). Цифры точности — кросс-валидация по данным организаторов и судья организаторов на их проверочном прогоне; цифры быстродействия — замеры в чистом ROS 2 Humble с лимитами жюри. Каждое число сопровождается источником.

## 1. Код

Репозиторий: https://github.com/MikeEgorshev/FunnyRepo (к сдаче должен быть **публичным** — требование с QA 25.09).

| Пакет | Что внутри |
|---|---|
| `src/tram_odometry` | Нода `tram_odometry_node`: подписки на `/vehicle/*` и GNSS (выставка и коррекция), выход `/result/velocity`, `/result/position`, `/result/diagnostics`. Модель тяги, EKF вдоль пути, карта линии, привязка к стоянкам. Чистый Python, внешних зависимостей нет |
| `src/tram_vehicle_msgs` | Сообщения организаторов (`VelocitySensor`, `DriverControllerCommand`) из основного датасета, с полем `<maintainer>`, без которого Humble пакет не собирает |

Сборка — `colcon build` без интернета.

## 2. Инструкция для жюри

### Сборка

```bash
source /opt/ros/humble/setup.bash
colcon build
source install/setup.bash
```

Или в Docker (образ на `ros:humble-ros-base`, сборка без сети):

```bash
docker build -f docker/Dockerfile -t tram-odometry .
```

В рабочем пространстве должен быть **один** пакет `tram_vehicle_msgs`. В пакете проверки организаторов (`check-code`) свой `tram_vehicle_msgs` — без `DriverControllerCommand`; организаторы разрешили взять пакет из основного датасета, это наш `src/tram_vehicle_msgs`. Два пакета с одним именем colcon не соберёт.

### Запуск на rosbag

```bash
ros2 launch tram_odometry tram_odometry.launch.py            # терминал 1
ros2 bag play <каталог прогона>                              # терминал 2
```

Номер трамвая можно задать параметром `vehicle_id:=30618` или `30639` (уточняет масштаб колёс). Без него берётся средний масштаб, дальше фильтр уточняет его сам.

Одной командой в Docker — нода, проигрывание bag и запись входов и выходов:

```bash
docker run --rm -v <каталог с bag>:/data -v $PWD/out:/out tram-odometry \
  sim.sh /data/<прогон> /out/<прогон>
```

С судьёй организаторов: собрать в одном рабочем пространстве наш `src/` и их `hackathon_solution_checker`, запустить `ros2 launch tram_odometry tram_odometry.launch.py`, `ros2 run hackathon_solution_checker metrics` и `ros2 bag play` их прогона — так получены цифры в разделе 5.

### Что ждать на выходе

| Топик | Тип | Содержимое |
|---|---|---|
| `/result/velocity` | `tram_vehicle_msgs/VelocitySensor` | продольная скорость, **м/с**; `frame_id: base_link` |
| `/result/position` | `nav_msgs/Odometry` | положение `base_link` в сетке MGRS (UTM 37N минус 300 000 / 6 100 000, как pathgraph и `/localization/kinematic_state`); курс по касательной к пути; скорость; ковариации. `frame_id: map`; без GNSS на старте — `odom`, относительная одометрия от старта |
| `/result/diagnostics` | `diagnostic_msgs/DiagnosticArray` | флаг проскальзывания, пропуски и зависания тележек, неопределённость положения, поправка масштаба колёс, время обработки |

`header.stamp` выхода — метка входа, который вызвал обновление. Если все входы молчат дольше 40 мс, нода публикует прогноз по модели с меткой «последний вход + прошедшее время», поэтому выход не реже 20 Гц даже при зависании датчиков.

### Логи, метрики, задержка

- Лог ноды — вывод `ros2 launch` (в Docker — `node.log` в каталоге результата).
- `research/claude/analyze_sim.py <результат sim> <id прогона>` — частота, сквозная задержка, точность против GNSS и ресурсы по записи `sim.sh`.
- `research/claude/check_bag.py <каталог прогона>` — офлайн те же метрики, что у судьи организаторов, по эталону `/localization/kinematic_state` из прогона.
- `scripts/realtime_check.py` — нагрузочная проверка без bag: синтетические входы с реальной частотой, задержка ответа на вход, разрывы выхода, CPU и память ноды; `--stall-at/--stall-s` глушат все входы.

## 3. Математическая модель

### Входы и выходы

Входы: позиция контроллера `u ∈ {−15…15}` (20 Гц), скорость передней и задней тележки в км/ч (по 10 Гц). GNSS: антенна master — выставка в первые 5 с и коррекция пути, если фиксы приходят по ходу (в проверочном прогоне организаторов — пачки по несколько секунд раз в 2–3 минуты); антенна rover — курс трамвая на стоянке при выставке. Скорость GNSS не используется. Выходы: продольная скорость `v` и положение `base_link`.

### Модель тяги и торможения

Масса неизвестна, поэтому модель задаёт ускорение на единицу массы:

```
a_model = A(u(t − τ), v),      τ = 0,4 с
```

`A` — таблица 31 × 16: строки — позиции контроллера −15…15, столбцы — узлы скорости 0,5…15,5 м/с, между узлами линейная интерполяция (`config/traction_table.csv`). Таблица идентифицирована по данным: средняя производная скорости колёс в ячейках «позиция × скорость», задержка отклика выбрана перебором (`research/claude/build_traction.py`). Она объясняет около 87 % дисперсии ускорения. По форме это «постоянная сила до базовой скорости, дальше постоянная мощность» для тяги и растущая с номером позиции тормозная сила. Ограничения: тормоз не разгоняет назад, более глубокая позиция не слабее.

### Фильтр вдоль пути

Состояние `x = [s, v, d, c]`: дистанция вдоль маршрута, м; скорость, м/с; возмущающее ускорение, м/с² (уклон, масса, ошибка модели); ошибка масштаба колёс — тележка показывает `v·(1 + c)`.

Прогноз с шагом до 0,1 с:

```
a  = A(u(t − τ), v) + d                (при v ≈ 0 торможение не даёт отрицательного ускорения)
s ← s + v·h + a·h²/2
v ← max(0, v + a·h)
d, c — случайное блуждание             (|d| ≤ 0,5 м/с², |c| ≤ 3 %)
F = [[1, h, h²/2, 0], [0, 1, h, 0], [0, 0, 1, 0], [0, 0, 0, 1]]
Q: σ_a = 0,25 м/с² — шум ускорения модели (1,0, если команда контроллера старше 0,3 с или
   модель только что разошлась с колёсами); σ_d = 0,02 м/с²/√с; σ_c = 2·10⁻⁵ /√с;
   σ_u = 0,2 м/√м — необъяснённая ошибка пути, растёт с пройденным путём
```

Измерение — скорость тележки: `z = v_км/ч / k = v·(1 + c) + шум`, `H = [0, 1 + c, 0, v]`, `R = σ_w² + (σ_w,rel · z)²`, `σ_w = 0,05 м/с`, `σ_w,rel = 0,01`; ковариация обновляется в форме Джозефа. По скорости тележки масштаб `c` не учится (он неотличим от ошибки модели) — только по привязкам к стоянкам и фиксам GNSS, через корреляцию `s` и `c`, накопленную с прошлой привязки. Масштаб колёс `k` = 3,5966 по умолчанию; для трамваев 30618 и 30639 — 3,5953 и 3,6106 (медианы по данным); априорное СКО `c` — 0,2 %.

### Обнаружение проскальзывания и сбоев датчиков

Отсчёт тележки не попадает в фильтр или попадает только как граница, если:

1. **Мусор на входе:** NaN, скорость вне −2…120 км/ч.
2. **Одиночный выброс:** скачок от прошлого показания этой тележки быстрее физически возможного и не подтверждён второй тележкой.
3. **Датчик завис:** 6 одинаковых ненулевых показаний подряд (в живых данных повторов 2–3).
4. **Проскальзывание по ускорению:** колесо разгоняется быстрее, чем позволяет модель тяги (буксование), или тормозит быстрее модели торможения (юз), и уже ушло от прогноза. Так ловится и одновременное проскальзывание обеих тележек, которое сравнение тележек не видит. Исключённое колесо остаётся границей: буксующее — верхней границей скорости, в юзе — нижней. Возврат колеса к скорости трамвая после буксования принимается сразу.
5. **Тележки расходятся** больше `max(0,3 м/с; 5 % v)`: в тяге подозрительна быстрая тележка, в торможении — медленная; показание, ушедшее от прогноза в невозможную для режима сторону (на ходу при тяге — ноль), — отказ этого датчика.
6. **Невязка с моделью велика:** `ν² > 9·S`. Если колёса расходятся с моделью дольше 3 с, ошиблась модель: скорость пересинхронизируется по колёсам. Если обе тележки при этом согласны между собой, а их ускорение физически возможно (разгон до 2 м/с², торможение до 5 м/с²), — через 0,6 с, и 3 с после этого модели доверие снижено. Так фильтр идёт за экстренным торможением, которого не видно по ручке контроллера (в данных: −4 м/с² при ручке 0).

Флаг проскальзывания публикуется в `/result/diagnostics`. Когда колёс нет, фильтр идёт только по модели, неопределённость растёт.

### Положение

Координаты берутся проекцией `s` на карту линии (`maps/route.csv`: точки через 1 м, замкнутый маршрут 11 030 м по откалиброванной `s`, построен офлайн по GNSS обучающих прогонов; с pathgraph организаторов совпадает с медианой 0,2 м). На западной конечной кольцо идёт через разворотную петлю — так её проходят 28 из 32 прогонов, доезжающих до развилки. У конечных — 15 отводов (`maps/route_spurs.csv`) для стартов вне основного кольца.

- **Выставка:** в окне 5 с точки GNSS master; на старте трамвай стоит, поэтому берётся медиана, одиночные прыжки дальше 10 м отбрасываются. Курс — по второй антенне (rover в 12,4 м впереди master) или по смещению, если трамвай сдвинулся больше 3 м: так на двухпутном участке выбирается путь нужного направления. `s` — проекция точки на карту или отвод.
- **Выходная точка:** `base_link` = антенна master + 9,873 м вперёд по пути, высота −3,0 м (tf от организаторов).
- **Привязка к стоянкам:** стоянка дольше 2 с у места регулярной стоянки (`maps/route_stops.csv`, 33 места) в гейте 3σ (не дальше 60 м) — калмановская поправка `s` и масштаба `c`. Неопределённость `s` растёт с путём после привязки: и от масштаба, и от необъяснённой ошибки σ_u.
- **Коррекция по GNSS:** фикс master после окна выставки проецируется на карту рядом с текущей оценкой (окно ±120 м) и поправляет `s` и `c` так же, как привязка (σ 2 м, не чаще раза в секунду). Фикс используется, только если соседний фикс (не старше 1,5 с) согласен с ним в пределах 3 м, он ближе 6 м к пути и невязка меньше 80 м. Выключается параметром `gnss_corrections: false`.
- **Без GNSS на старте** (такое возможно, сказали на QA): относительная одометрия, `x = s`, `frame_id: odom`.

## 4. Допущения и параметры

### Допущения

- Проверочные прогоны идут по той же линии, что и обучающие (подтверждено на QA и в чате капитанов: «только регулярный маршрут»). Карта и места стоянок построены по обучающим данным — это разрешено.
- Трамвай не едет назад: в данных отрицательных скоростей нет.
- Скорость тележек — в км/ч. Масштаб колёс меняется от прогона к прогону (разброс 0,3 % у 30618 и 0,7 % у 30639, до 1,4 %) и уточняется по ходу прогона.
- Таблица тяги одна на оба трамвая одной модели; разница масс (один чаще с пассажирами) уходит в возмущение `d`.
- GNSS — только положение: выставка на старте и коррекция по фиксам, если они приходят по ходу («для начальной выставки и коррекции» — описание задачи; организаторы подтвердили, что коррекция оценку не снижает). Скорость — только колёса и модель.

## 5. Точность и быстродействие

### Методика точности

`research/claude/cv.py`: двухкратная кросс-валидация. Карта, отводы и места стоянок строятся по одной половине прогонов, проверка — на другой; точные дубликаты прогонов держатся в одной половине, две опорные поездки карты (съёмка маршрута) — в обучении обеих половин. Прогон воспроизводится по времени записи, как `ros2 bag play`. GNSS подаётся как в проверочном прогоне организаторов: первые 21 с и пачки по 2 с раз в 150 с. Эталон — `base_link` по двум антеннам GNSS в той же сетке MGRS; выход и эталон сопоставляются по ближайшей метке с допуском 0,05 с, как у судьи. Оценено 77 прогонов: у остальных GNSS нет вовсе (оценивать не по чему) или прогон короче минуты, а две опорные поездки карты в проверку не входят.

Остаток RMSE скорости до 0,7 м/с на худших прогонах — сбои самого эталона GNSS (скорость 0 на ходу).

### Проверочный прогон организаторов и их судья

Прогон `30618_88aea4d9` из пакета проверки (21,9 мин, 5,5 км, с эталоном `/localization/kinematic_state`); их `hackathon_solution_checker` в ROS 2 Humble, Docker `--cpus=2 --memory=512m`, `ros2 bag play` 1:1, `vehicle_id:=30618`:

| Версия | RMSE скорости, м/с | RMSE x / y / z, м | RMSE 3D, м | 3D макс., м |
|---|---|---|---|---|
| сдаваемая (`main`, с коррекцией по GNSS) | 0,042 | 3,93 / 4,62 / 0,18 | 6,07 | 49,6 |
| без коррекции по GNSS | 0,040 | 3,41 / 4,68 / 0,18 | 5,79 | 48,5 |

Офлайн (`check_bag.py`) — то же: 0,038 м/с, RMSE 3D 6,05 м, средняя 3D-ошибка 2,06 м.

**Где набирается ошибка.** Pathgraph организаторов (`materials/pathgraph/`, «карта путей») в обоих направлениях кончается примерно за 80 м до развилки у западной конечной: разворотной петли и тупика отстоя в нём нет. На участке, который он покрывает (77 % времени прогона), RMSE 3D — **2,0 м**, максимум 6,9 м. Весь остальной RMSE — пути конечной за пределами pathgraph: в последние 35 с трамвай уходит с кольца не в петлю, а в тупик (так в данных заканчиваются 4 заезда из 32), и ошибка вырастает до 49 м. Без датчика курса и без GNSS ветку на стрелке не видно: последняя пачка GNSS в этом прогоне приходит за 5 с до развилки. Карта по умолчанию ведёт трамвай по петле, потому что так проходят 28 заездов из 32.

### Устойчивость к проскальзыванию и сбоям датчиков

## 6. Ограничения и план развития

### Ограничения

- **Развилка у западной конечной — за пределами pathgraph организаторов.** Кольцо карты одно и идёт через петлю; часть трамваев (4 заезда из 32, в том числе проверочный) уходит в тупик отстоя. Ручка контроллера и скорости тележек ветку на стрелке не показывают, поэтому без фикса GNSS после развилки фильтр ведёт трамвай по петле, и ошибка к концу прогона вырастает до 50 м. На маршруте pathgraph этой проблемы нет: там RMSE 3D проверочного прогона — 2,0 м.
- **Сильный шум колёс.** При белом шуме тележек σ = 1 км/ч (в 5 раз выше, чем в данных) ошибка положения растёт на ~14 м: шумные показания принимаются за начало проскальзывания.
- **Без GNSS на старте** — только относительная одометрия: путь от старта, без привязки к карте и стоянкам.
- **Масштаб колёс** учится по привязкам и фиксам GNSS осторожно (СКО 0,2 %): смелее — ложная привязка (светофор рядом со стоянкой) уходит в масштаб. На прогонах с ошибкой масштаба больше 1 % остаётся дрейф.
- **Эталон в кросс-валидации** — две антенны GNSS; у судьи — `/localization/kinematic_state` (слияние GNSS и лидарной одометрии). На проверочном прогоне обе методики дают одно и то же.
- **Таблица тяги** снята по двум трамваям в мае–сентябре; при другой загрузке и погоде её точность ниже, это компенсирует возмущение `d`.

### План после хакатона

1. Отводы на прибытие у конечных и выбор ветки по GNSS и по месту стоянки.
2. Использовать уклон из карты высот как известную часть возмущения.
3. Определять номер трамвая по данным: масштаб колёс и отклик на позиции контроллера различаются.
4. Устойчивость к шуму колёс: оценивать дисперсию показаний онлайн и поднимать пороги детектора.
5. Перенести горячий путь на C++, если потребуется меньшая задержка на слабом вычислителе.
