# Решение: резервная одометрия трамвая по модели

Документ для формы сдачи: разделы совпадают с её полями (см. [форму](context/2026-09-25-submission-form.md)). Цифры точности — из кросс-валидации по данным организаторов, цифры быстродействия — из замера в чистом ROS 2 Humble с лимитами жюри. Каждое число сопровождается источником.

## 1. Код

Репозиторий: https://github.com/MikeEgorshev/FunnyRepo (к сдаче должен быть **публичным** — требование с QA 25.09).

| Пакет | Что внутри |
|---|---|
| `src/tram_odometry` | Нода `tram_odometry_node`: подписки на `/vehicle/*`, выход `/result/velocity`, `/result/position`, `/result/diagnostics`. Модель тяги, EKF вдоль пути, карта линии, привязка к стоянкам. Чистый Python, внешних зависимостей нет |
| `src/tram_vehicle_msgs` | Сообщения организаторов (`VelocitySensor`, `DriverControllerCommand`) |

Сборка — `colcon build` без интернета.

## 2. Инструкция для жюри

### Сборка

```bash
source /opt/ros/humble/setup.bash
colcon build
source install/setup.bash
```

Или в Docker (образ на `ros:humble-ros-base`, сборка без сети):

```bash
docker build -f docker/Dockerfile -t tram-odometry .
```

### Запуск на rosbag

```bash
ros2 launch tram_odometry tram_odometry.launch.py            # терминал 1
ros2 bag play <каталог прогона>                              # терминал 2
```

Номер трамвая можно задать параметром `vehicle_id:=30618` или `30639` (уточняет масштаб колёс). Без него берётся средний масштаб.

Одной командой в Docker — нода, проигрывание bag и запись входов и выходов:

```bash
docker run --rm -v <каталог с bag>:/data -v $PWD/out:/out tram-odometry \
  sim.sh /data/<прогон> /out/<прогон>
```

### Что ждать на выходе

| Топик | Тип | Содержимое |
|---|---|---|
| `/result/velocity` | `tram_vehicle_msgs/VelocitySensor` | продольная скорость, **м/с**; `frame_id: base_link` |
| `/result/position` | `nav_msgs/Odometry` | положение `base_link` в сетке MGRS (UTM 37N минус 300 000 / 6 100 000, как pathgraph и `/localization/kinematic_state`); курс по касательной к пути; скорость; ковариации. `frame_id: map`; без GNSS на старте — `odom`, относительная одометрия от старта |
| `/result/diagnostics` | `diagnostic_msgs/DiagnosticArray` | флаг проскальзывания, пропуски и зависания тележек, неопределённость положения, время обработки |

`header.stamp` выхода — метка входа, который вызвал обновление. Если все входы молчат дольше 40 мс, нода публикует прогноз по модели с меткой «последний вход + прошедшее время», поэтому выход не реже 20 Гц даже при зависании датчиков.

### Логи, метрики, задержка

- Лог ноды — вывод `ros2 launch` (в Docker — `node.log` в каталоге результата).
- `research/claude/analyze_sim.py <результат sim> <id прогона>` — частота, сквозная задержка, точность против GNSS и ресурсы по записи `sim.sh`.
- `scripts/realtime_check.py` — нагрузочная проверка без bag: синтетические входы с реальной частотой, задержка ответа на вход, разрывы выхода, CPU и память ноды; `--stall-at/--stall-s` глушат все входы.

## 3. Математическая модель

### Входы и выходы

Входы: позиция контроллера `u ∈ {−15…15}` (20 Гц), скорость передней и задней тележки в км/ч (по 10 Гц). GNSS master — только выставка в первые 5 с. Выходы: продольная скорость `v` и положение `base_link`.

### Модель тяги и торможения

Масса неизвестна, поэтому модель задаёт ускорение на единицу массы:

```
a_model = A(u(t − τ), v),      τ = 0,4 с
```

`A` — таблица 31 × 16: строки — позиции контроллера −15…15, столбцы — узлы скорости 0,5…15,5 м/с, между узлами линейная интерполяция (`config/traction_table.csv`). Таблица идентифицирована по данным: средняя производная скорости колёс в ячейках «позиция × скорость», задержка отклика выбрана перебором (`research/claude/build_traction.py`). Она объясняет около 87 % дисперсии ускорения. По форме это «постоянная сила до базовой скорости, дальше постоянная мощность» для тяги и растущая с номером позиции тормозная сила. Ограничения: тормоз не разгоняет назад, более глубокая позиция не слабее.

### Фильтр вдоль пути

Состояние `x = [s, v, d]`: дистанция вдоль маршрута, м; скорость, м/с; возмущающее ускорение, м/с² (уклон, масса, ошибка модели).

Прогноз с шагом до 0,1 с:

```
a  = A(u(t − τ), v) + d                (при v ≈ 0 торможение не даёт отрицательного ускорения)
s ← s + v·h + a·h²/2
v ← max(0, v + a·h)
d ← d                                   (случайное блуждание, |d| ≤ 0,5 м/с²)
F = [[1, h, h²/2], [0, 1, h], [0, 0, 1]]
Q: σ_a = 0,25 м/с² — белый шум ускорения модели; σ_d = 0,02 м/с²/√с — блуждание d
```

Измерение — скорость тележки: `z = v_км/ч / k · (1 + scale)`, `H = [0, 1, 0]`, дисперсия `R = σ_w² + (σ_w,rel · z)²`, где `σ_w = 0,05 м/с`, `σ_w,rel = 0,01`. Масштаб колёс `k` = 3,5966 по умолчанию; для трамваев 30618 и 30639 — 3,5953 и 3,6106 (медианы по данным).

### Обнаружение проскальзывания и сбоев датчиков

Отсчёт тележки не попадает в фильтр, если:

1. **Невязка велика:** `(z − v)² > 9·(P_vv + R)` — выброс, буксование или юз. Если колёса расходятся с моделью дольше 3 с и согласованно, ошиблась модель: скорость пересинхронизируется по колёсам.
2. **Тележки расходятся** больше `max(0,3 м/с; 5 % v)`: в тяге подозрительна быстрая тележка (буксует), в торможении — медленная (юз).
3. **Датчик завис:** 6 одинаковых ненулевых показаний подряд (в живых данных повторов 2–3).
4. **Мусор на входе:** NaN, скорость вне −2…120 км/ч.

Флаг проскальзывания публикуется в `/result/diagnostics`. Когда колёс нет, фильтр идёт только по модели, неопределённость растёт.

### Положение

Координаты берутся проекцией `s` на карту линии (`maps/route.csv`, точки через 1 м, замкнутый маршрут 10 988 м, построен офлайн по GNSS обучающих прогонов; с pathgraph организаторов совпадает с медианой 0,2 м). У конечных — 16 отводов (`maps/route_spurs.csv`) для стартов вне основного кольца.

- **Выставка:** в окне 5 с точки GNSS master; на старте трамвай стоит, поэтому берётся медиана, одиночные прыжки дальше 10 м отбрасываются. Курс — по смещению, если трамвай сдвинулся больше 3 м. `s` — проекция точки на карту или отвод.
- **Выходная точка:** `base_link` = антенна master + 9,873 м вперёд по пути, высота −3,0 м (tf от организаторов).
- **Привязка к стоянкам:** стоянка дольше 2 с и место регулярной стоянки (`maps/route_stops.csv`, 32 места) в гейте 3σ — одномерная поправка `s`. Неопределённость `s` растёт с путём после привязки: `σ_s² = P_ss + (0,004·d)²`.
- **Без GNSS на старте** (такое возможно, сказали на QA): относительная одометрия, `x = s`, `frame_id: odom`.

## 4. Допущения и параметры

### Допущения

- Проверочные прогоны идут по той же линии, что и обучающие (подтверждено на QA). Карта и места стоянок построены по обучающим данным — это разрешено.
- Трамвай не едет назад: в данных отрицательных скоростей нет.
- Скорость тележек — в км/ч; масштаб колёс постоянен в пределах прогона.
- Таблица тяги одна на оба трамвая одной модели; разница масс (один чаще с пассажирами) уходит в возмущение `d`.
- GNSS в контуре не участвует: только выставка в первые 5 с.

## 5. Точность и быстродействие

### Методика точности

`research/claude/cv.py`: двухкратная кросс-валидация. Карта, отводы и места стоянок строятся по одной половине прогонов, проверка — на другой; точные дубликаты прогонов держатся в одной половине. Прогон воспроизводится по времени записи, как `ros2 bag play`; GNSS доступен только в первые 5 с. Эталон — `base_link` по двум антеннам GNSS в той же сетке MGRS; выход и эталон сопоставляются по ближайшей метке с допуском 0,05 с. Оценено 79 прогонов (в 35 прогонах GNSS нет вообще, оценивать не по чему).

## 6. Ограничения и план развития

### Ограничения

- **Масштаб колёс у 30639.** Его `k` по прогонам делится на две группы (3,586–3,590 и 3,617–3,658), фиксированное значение ошибается примерно на 0,6 %. Отсюда втрое большая ошибка положения у этого трамвая. Онлайн-подстройка масштаба по привязкам сейчас выключена (`scale_adapt = 0`).
- **Гейт привязки к стоянкам** учитывает ошибку масштаба 0,4 % на пройденный путь, а реальные ошибки доходят до 1,4 %. На прогонах с сильной ошибкой масштаба привязка может не срабатывать.
- **Эталон в нашей оценке** — две антенны GNSS, а у судьи — `/localization/kinematic_state` (слияние GNSS и лидарной одометрии). Абсолютные цифры у судьи могут отличаться; на шумных участках GNSS наша оценка, вероятно, пессимистична.
- **Хвост ошибок.** Худший прогон (`30639_9c362687`, RMSE 3D 124,6 м) стартует у конечной на пути, которого нет в карте его половины кросс-валидации: выставка цепляется за соседний путь. Следующие два (`30618_defd0170` — 46,5 м, `30639_d601d28f` — 42,5 м) — прогоны с самой большой ошибкой масштаба колёс, около 1,4 %.
- **Таблица тяги** снята по двум трамваям в сентябре; при другой загрузке и погоде её точность ниже, это компенсирует возмущение `d`.

### План после хакатона

1. Онлайн-оценка масштаба колёс по расстояниям между привязками к стоянкам (путь по карте против пути по одометрии, с весом по разбросу мест стоянок) и более широкий гейт, растущий с неопределённостью масштаба.
2. Использовать уклон из карты высот как известную часть возмущения.
3. Определять номер трамвая по данным: масштаб колёс и отклик на позиции контроллера различаются.
4. Проверить точность против `/localization/kinematic_state`, когда организаторы дадут эталон.
5. Перенести горячий путь на C++, если потребуется меньшая задержка на слабом вычислителе.
