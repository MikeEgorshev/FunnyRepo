# AGENTS.md — правила работы в репозитории

Общие правила для людей команды и **всех ИИ-агентов** (Claude Code, Codex, Cursor, Gemini CLI, Copilot и др.). Прочитай файл целиком до первого коммита. Если твой инструмент не подхватывает `AGENTS.md` сам, человек, который тебя запускает, даёт его первым сообщением.

Правила обязательны. Нужно отступить от правила — спроси человека в чате и дождись явного «да». Менять этот файл может только лид.

## Коротко: 12 правил

1. В `main` — только через PR. Никаких прямых коммитов и `push` в `main`.
2. Одна задача = одна ветка = один PR. У каждого агента свой worktree. Два агента в одной папке — нельзя.
3. Имя ветки: `<префикс>/<issue>-<тема>`, например `claude/12-slip-detector`.
4. Перед началом работы, каждые ~2 часа и перед PR: `git fetch origin && git rebase origin/main`.
5. Коммиты маленькие, в формате Conventional Commits. `git add <файлы>`, а не `git add -A` вслепую.
6. Меняй только файлы своей задачи. Никакого попутного рефакторинга, массового форматирования и переименований.
7. Интерфейсы (топики, сообщения, параметры, единицы, фреймы) меняются только отдельным PR по согласованию с лидом.
8. Никаких `push --force`, `reset --hard`, `clean -fdx`, `--no-verify` и переписывания чужой истории.
9. В git не попадают данные, rosbag, файлы больше 5 МБ, секреты и `build/ install/ log/`.
10. В PR — что сделано и как проверено: точные команды и результат. Не запускал — так и пиши.
11. Мержит в `main` только человек. Агент не нажимает merge.
12. Непонятно, конфликт в чужом коде, хочется нарушить правило — остановись и спроси человека.

## Структура репозитория

Предлагаемая, лид может менять.

```
src/                 # colcon-пакеты ROS 2 (C++/Python)
research/<автор>/    # ноутбуки и эксперименты: у каждого своя папка
docs/context/        # материалы организаторов и транскрипты созвонов — текстом
docs/interfaces.md   # контракт между частями: топики, типы, единицы, фреймы
docs/decisions/      # ключевые решения, по файлу на решение: ГГГГ-ММ-ДД-тема.md
data/                # локальные данные; в git только data/README.md
scripts/             # утилиты: конвертация данных, метрики
```

`docs/context/` — общая память команды и агентов: полное описание задачи, критерии оценки, формат решения, ответы организаторов, транскрипты созвонов (`ГГГГ-ММ-ДД-тема.md`). Туда только добавляем новые файлы, существующие не переписываем. Аудио и видео в git не кладём — только ссылку на запись.

## 2. Задачи: не делать одно и то же дважды

- Источник правды — GitHub Issues: одна задача = один issue = одна ветка = один PR.
- Перед стартом убедись, что задачу никто не взял: у issue нет исполнителя и комментария «Взял», нет ветки и PR по нему (`git fetch --prune && git branch -r`, `gh pr list`).
- Взял задачу — сразу отметь: комментарий в issue «Взял: <агент>, ветка `<ветка>`», после первого пуша — Draft PR. Нет доступа к GitHub — отмечает человек, который тебя запустил.
- Без issue работаешь только по прямому поручению человека; тогда укажи это в PR.
- Задача больше чем на полдня — разбей на несколько issue.

## 3. Ветки и worktree

- `main` всегда собирается и проходит тесты. Первый коммит с этими правилами — единственный прямой коммит в `main`.
- Имя ветки: `<префикс>/<номер issue>-<тема>` — латиница, нижний регистр, дефисы: `claude/12-slip-detector`, `codex/7-ros-node-skeleton`, `mike/fix-launch-params`.
- Каждый агент работает в своём worktree (или своём клоне). Два агента в одной папке затирают друг другу незакоммиченные изменения, индекс и `build/`. Worktree держи вне папки репозитория:

  ```bash
  git fetch origin
  git worktree add -b claude/12-slip-detector ../FunnyRepo-wt/claude-12 origin/main
  cd ../FunnyRepo-wt/claude-12
  ```

- В чужие ветки не коммить. Нужен чужой незамерженный код — дождись мержа или ответвись от чужой ветки и напиши в PR `Depends on #N`.
- Ветка живёт не дольше дня, лучше — несколько часов. После мержа удали свой worktree и локальную ветку (см. шпаргалку).

## 4. Синхронизация

- В своей ветке не делай `git pull` — только `git fetch origin && git rebase origin/main`: история остаётся линейной, без merge-коммитов.
- Ребейз — перед началом работы, примерно каждые 2 часа и обязательно перед переводом PR в Ready.
- Пушь свою ветку хотя бы раз в 1–2 часа, чтобы остальные видели прогресс. Первый пуш: `git push -u origin HEAD`.
- После ребейза уже запушенной ветки: `git push --force-with-lease` — только в свою ветку.
- Замержили изменение интерфейсов — все, кого оно касается, сразу ребейзятся.

## 5. Коммиты

- Один коммит — одно логическое изменение. Коммить часто.
- Формат [Conventional Commits](https://www.conventionalcommits.org/ru/v1.0.0/): `<тип>(<область>): <что сделано>`. Заголовок — на английском, в повелительном наклонении, до 72 символов. Тело (зачем и как) можно по-русски.

  ```
  feat(model): add traction force model from controller position
  fix(odom): ignore wheel speed spikes on sensor dropout
  test(estimator): cover slip detection on wet rail
  ```

  Типы: `feat`, `fix`, `refactor`, `perf`, `test`, `docs`, `build`, `ci`, `chore`, `exp` (эксперименты в `research/`). Области: `model`, `estimator`, `ros`, `msgs`, `launch`, `data`, `research`, `docs`, `ci` — добавляй по мере надобности.
- В конце сообщения — ссылка на задачу: `Refs #12` или `Closes #12`.
- Перед коммитом — `git status` и `git diff --staged`. Добавляй конкретные файлы: `git add src/... test/...`. `git add -A` и `git add .` — только если `git status` показывает исключительно твои изменения.
- Не создавай отчётных файлов вроде `SUMMARY.md`, `NOTES.md`, `CHANGES.md`: отчёт пишется в описание PR.

## 6. Границы изменений

- Меняй только то, что нужно для твоей задачи. Заметил проблему в другом месте — заведи issue или напиши в PR, но не чини попутно.
- Никакого массового форматирования, переименований, переносов файлов и обновления зависимостей вне отдельной задачи. Форматтер запускай только на изменённых тобой файлах.
- Не ослабляй и не удаляй чужие тесты, чтобы прошёл твой PR. Упал чужой тест — разберись или спроси.
- Новая внешняя зависимость (пакет ROS, pip, системная библиотека) — только с согласия лида и с упоминанием в PR.
- Только через лида и отдельным PR: `AGENTS.md`, `CLAUDE.md`, `.github/`, `.gitattributes`, `docs/interfaces.md`, пакеты сообщений `*_msgs`. В `.gitignore` строки можно добавлять, но не удалять.

## 7. Интерфейсы — контракт между частями

Модель, оценщик и ноды ROS пишут параллельно разные люди и агенты. Чтобы части стыковались, контракт фиксируется в `docs/interfaces.md` (его заводит лид первым PR после получения данных):

- имена топиков, типы сообщений, частоты и QoS;
- единицы — только СИ: м, м/с, м/с², рад;
- фреймы (`map`, `odom`, `base_link`) и параметры нод.

Изменение контракта — отдельный PR `feat(interfaces): …` с согласия лида. Пока он не замержен, другие ветки на него не опираются.

## 8. Pull Request

- Открывай PR сразу после первого пуша, как Draft. Готово — переводи в Ready for review.
- Заголовок — в формате коммита: при squash merge он станет коммитом в `main`.
- Описание — по шаблону `.github/pull_request_template.md`: что и зачем, как проверено (точные команды и результат), интерфейсы, зависимости, кто автор.
- Размер — до ~400 строк изменений в коде. Больше — дели на несколько PR.
- Перед Ready: ребейз на свежий `origin/main`, локально проходят `colcon build` и `colcon test`. Когда появится CI, зелёный CI обязателен.
- Ревью: хотя бы один участник, кроме автора, — человек или другой агент. Перекрёстное ревью приветствуется: Claude смотрит PR от Codex и наоборот.
- Мерж — только человек: лид или тот, кто запускает агента-автора, после ревью. Способ — **Squash and merge**, ветку после мержа удалить. PR, которые трогают защищённые файлы (§6) или интерфейсы (§7), мержит только лид.
- Заканчиваешь сессию (конец работы, лимит контекста) — всё закоммичено и запушено, в PR написано: что сделано, что осталось, известные проблемы.

## 9. Конфликты

- Конфликты решает тот, чей PR мержится позже: ребейз на `origin/main` и разрешение в своей ветке.
- Сохраняй смысл обеих сторон. Не бери целиком «свою» или «их» версию файла, который правил не ты.
- После разрешения — сборка и тесты.
- Конфликт в чужой зоне или в интерфейсах, непонятно, чья версия правильная, — остановись и спроси человека.

## 10. Запрещено без явного разрешения человека

- любой `push` в `main`; `git push --force` куда угодно (в свою ветку — только `--force-with-lease`);
- `git reset --hard`, `git clean -fdx`, `git checkout -- .`, `git restore .`, `git stash drop` / `clear`: они уничтожают незакоммиченную работу и локальные данные;
- `git commit --amend` и `git rebase -i` уже запушенных коммитов в ветке, где работает кто-то ещё;
- `--no-verify`, отключение хуков, правка CI ради «зелёного»;
- удаление чужих веток, любых тегов и релизов;
- `git config --global`, изменение `remote`, настройки репозитория на GitHub;
- мерж PR;
- коммит секретов, токенов, `.env`, персональных данных.

## 11. Что не коммитим

- `build/ install/ log/` (colcon), `__pycache__/`, `.venv/`, файлы IDE — уже в `.gitignore`.
- Данные: датасеты, rosbag (`*.db3`, `*.mcap`, `*.bag`), выгрузки — в `data/`, она в `.gitignore`. Откуда брать данные — в `data/README.md`.
- Любой файл больше 5 МБ. Небольшие фикстуры для тестов (до 1 МБ) можно — в `test/` пакета.
- Ноутбуки — только в `research/<автор>/` и с очищенными выводами.
- Записи созвонов (аудио, видео) — только ссылкой; транскрипт — текстом в `docs/context/`.
- Секреты — никогда. Закоммитил секрет — сразу скажи лиду: секрет считается скомпрометированным и перевыпускается. Историю сам не переписывай.

## 12. Параллельный запуск ROS 2 на одной машине

- Каждый агент собирает и запускает всё в своём worktree, со своими `build/ install/ log/`. Не делай `source` чужого `install/setup.bash`.
- У каждого свой `ROS_DOMAIN_ID` (таблица в §1) и `ROS_LOCALHOST_ONLY=1`. Иначе ноды разных агентов видят топики друг друга, и тесты с замерами перемешиваются:

  ```bash
  export ROS_DOMAIN_ID=11 ROS_LOCALHOST_ONLY=1
  ```

- Закончил проверку — останови свои ноды и `ros2 launch`. Не оставляй фоновые процессы.

## 14. Если что-то пошло не так

- Сломался `main` — откат через PR: `git revert <sha>`. Не force-push.
- Случайно закоммитил в локальный `main` — перенеси работу в ветку: `git switch -c <префикс>/<тема>`, затем `git branch -f main origin/main`, и продолжай в ветке.
- Потерял коммит — смотри `git reflog`, ничего не удаляй и позови человека.
