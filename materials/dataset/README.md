# Датасет кейса «Резервная одометрия по модели» (беспилотный трамвай)

Набор данных для кейса **«Резервное позиционирование без GNSS»** хакатона Московского
транспорта. Содержит записанную телеметрию трамвая в формате **ROS 2 bag (rosbag2,
sqlite3)** и предназначен для разработки и офлайн-калибровки решения, которое оценивает
**скорость и положение** трамвая **без GNSS и без инерциальных датчиков** — только по
внутренней телеметрии (положение контроллера водителя и скорости вращения колёс).


---

## 1. Состав папки `dataset/`

| Файл / папка | Что это |
|--------------|---------|
| `data.zip` | Основной датасет — архив с ROS 2 bag-файлами телеметрии (см. ниже). |
| `tram_vehicle_msgs/` | ROS 2-пакет с определениями кастомных типов сообщений (`VelocitySensor`, `DriverControllerCommand`). Нужен для чтения топиков `/vehicle/*` и для публикации `/result/velocity`. |
| `README.md` | Этот файл. |

## 2. Что внутри `data.zip`

Распакованный архив содержит **122 отдельных ROS 2 bag** — по одному каталогу на прогон:

```
<bag_id>/
├── <bag_id>_0.db3      # данные (SQLite3, сериализация CDR)
└── metadata.yaml       # метаданные rosbag2 (версия 5): топики, типы, длительность, счётчики
```

Каждый `<bag_id>` имеет вид `<vehicle>_<hash>`, например `30618_0e41eac3`.
Числовой префикс — идентификатор записи/трамвая, их два:

| Префикс | Кол-во прогонов |
|---------|-----------------|
| `30618_` | 103 |
| `30639_` | 19  |
| **Всего** | **122** |

Сводка по объёму:

- суммарная длительность прогонов ≈ **36,7 часа**;
- длительность одного прогона: от **~1,3 c** до **~31,6 мин** (медиана ≈ 20 мин);
- суммарно ≈ **8,8 млн** сообщений; распакованный объём ≈ **825 МБ**.

Прогоны различаются по длине, режимам движения (разгоны, торможения, остановки) и
наличию сложных участков (проскальзывание, шум/пропуски). Короткие прогоны удобны для
быстрой отладки, длинные — для оценки накопленного дрейфа.

## 3. Топики

Во **всех 122 прогонах** присутствует один и тот же набор из 7 топиков.

### 3.1. Входные данные решения (разрешены в основном контуре)

Только эти три топика можно использовать для оценки скорости и положения:

| Топик | Тип сообщения | Смысл |
|-------|---------------|-------|
| `/vehicle/front_bogie_velocity` | `tram_vehicle_msgs/msg/VelocitySensor` | Скорость передней тележки (колёс) |
| `/vehicle/rear_bogie_velocity`  | `tram_vehicle_msgs/msg/VelocitySensor` | Скорость задней тележки (колёс) |
| `/vehicle/driver_position_cmd`  | `tram_vehicle_msgs/msg/DriverControllerCommand` | Положение ручки контроллера водителя |

### 3.2. Эталон / ground truth (только для расчёта метрик, НЕ для основного контура)

GNSS-топики служат **эталоном** для оценки точности и для начальной выставки/инициализации.
В отложенных проверочных прогонах наличие GNSS **гарантируется только в первые несколько
секунд**, поэтому опираться на них в рабочем режиме нельзя.

| Топик | Тип сообщения | Смысл |
|-------|---------------|-------|
| `/sensing/gnss/master/fix`  | `sensor_msgs/msg/NavSatFix`        | Положение (lat/lon/alt), приёмник **master** |
| `/sensing/gnss/master/vel`  | `geometry_msgs/msg/TwistStamped`   | Скорость, приёмник **master** |
| `/sensing/gnss/rover/fix`   | `sensor_msgs/msg/NavSatFix`        | Положение (lat/lon/alt), приёмник **rover** |
| `/sensing/gnss/rover/vel`   | `geometry_msgs/msg/TwistStamped`   | Скорость, приёмник **rover** |

> ⚠️ Использование GNSS/IMU/лидара/камер в **основном** контуре оценки — дисквалифицирующее
> условие по технической части. GNSS допустим
> только как эталон для метрик и для начальной инициализации положения.

## 4. Формат сообщений

### 4.1. Пользовательские типы `tram_vehicle_msgs`

Топики `/vehicle/*` (и выходной `/result/velocity`) используют **нестандартные** типы из
пакета **`tram_vehicle_msgs`**. Пакет приложен к датасету — папка
[`tram_vehicle_msgs/`](tram_vehicle_msgs/). Его нужно собрать в вашем ROS 2 workspace,
иначе `ros2 bag play` и десериализация кастомных топиков работать не будут.

Пакет содержит два определения:

**`msg/VelocitySensor.msg`** — продольная скорость тележки (колёс), м/с:

```
std_msgs/Header header
float64 velocity
```

**`msg/DriverControllerCommand.msg`** — положение ручки контроллера водителя:

```
std_msgs/Header header
int8 position
```

Значения `position`: `0` — нейтраль, `+1…+15` — ходовые (тяговые) позиции (разгон),
`−1…−15` — тормозные позиции. `header.frame_id` в записях: `base_link` у `VelocitySensor`
и пустой у `DriverControllerCommand`.


### 4.2. Стандартные типы (эталон)

- **`sensor_msgs/msg/NavSatFix`** — `header`, `status`, `latitude`, `longitude`,
  `altitude`, `position_covariance[9]`, `position_covariance_type`.
- **`geometry_msgs/msg/TwistStamped`** — `header` + `twist` (`linear.{x,y,z}`,
  `angular.{x,y,z}`); скорость в `twist.linear` (м/с).

## 5. Что нужно сделать (кратко)

Разработать пакет(ы) **ROS 2 Humble**, который в реальном времени по трём входным топикам
(`front_bogie_velocity`, `rear_bogie_velocity`, `driver_position_cmd`) оценивает скорость и
положение трамвая и **непрерывно публикует два выходных топика**:

| Выходной топик | Тип | Где лежит значение |
|----------------|-----|--------------------|
| `/result/velocity` | `tram_vehicle_msgs/msg/VelocitySensor` | оценённая продольная скорость (м/с) в поле **`velocity`** |
| `/result/position` | `nav_msgs/msg/Odometry`                | оценённое положение в **`pose.pose.position`** (`x`, `y`, `z`) |

### 5.1. Формат решения для автоматической проверки

Решение проверяется автоматическим скриптом-судьёй жюри, который слушает ваши выходные
топики и сравнивает их с эталоном. Чтобы прогон засчитался, соблюдайте контракт **точно**:

- **Имена и типы топиков — ровно как выше.** Скалярная скорость берётся из поля `velocity`
  сообщения `VelocitySensor`; положение — из `pose.pose.position` сообщения `Odometry`.
- **Заполняйте `header.stamp`** в обоих сообщениях временем соответствующего входа (временем
  из bag), а не «стенными» часами. Судья синхронизирует ваш результат с эталоном по
  ближайшей метке времени с допуском **~0.05 с**; при нулевых/сбитых `stamp` пары не
  сопоставляются и метрика не считается. Рекомендуется заполнять и `header.frame_id`.
- **Положение — в локальной метрической системе координат** (метры), согласованной с
  эталонной траекторией; сравнивается покомпонентно (`x/y/z`) и по 3D-расстоянию.
- **QoS:** судья подписывается best-effort и совместим с любым издателем; издавать можно с
  QoS по умолчанию (reliable) или best-effort.
- **Только онлайн-публикация** во время воспроизведения bag: пакетная постобработка и запись
  результатов «одним куском» в конце не засчитываются.
- Эталон, с которым сравнивают результат, формируется организаторами из GNSS-телеметрии;
  **сами GNSS-топики публиковать в решении не нужно** — только `/result/velocity` и
  `/result/position`.

### 5.2. Ключевые ограничения

- без GNSS/IMU/лидара/камер в основном контуре; GNSS — только эталон и начальная выставка;
- нельзя использовать данные «из будущего»; только непрерывная онлайн-публикация (не пакетная постобработка);
- реальное время: задержка «вход → результат» ≤ 100 мс, частота публикации ≥ 10 Гц;
- офлайн-калибровка параметров модели допустима

## 6. Как работать с датасетом

### 6.1. Распаковка и сборка пакета сообщений

```bash
# распаковать bag-файлы
unzip data.zip -d data/
# получите data/30618_xxxxxxxx/, data/30639_xxxxxxxx/, ...

# собрать пакет кастомных сообщений в своём ROS 2 workspace
#   (скопируйте папку tram_vehicle_msgs/ в <ws>/src/ рядом со своими пакетами)
cd <ros2_ws>
colcon build --packages-select tram_vehicle_msgs
source install/setup.bash
```

### 6.2. Осмотр bag через ROS 2 (нужен ROS 2 Humble + собранный `tram_vehicle_msgs`)

```bash
# краткая сводка по прогону: топики, типы, длительность, число сообщений
ros2 bag info data/30618_0e41eac3

# воспроизведение в реальном времени (публикует все топики bag)
ros2 bag play data/30618_0e41eac3

# в реальном времени можно смотреть входные топики
ros2 topic echo /vehicle/driver_position_cmd
ros2 topic echo /vehicle/front_bogie_velocity
```

Типичный сценарий проверки решения: запустить свою ноду, затем `ros2 bag play <bag>` и
наблюдать публикацию `/result/velocity` и `/result/position`.

> Чтобы `ros2 bag play`/`info` понимали типы `tram_vehicle_msgs`, соберите пакет
> `tram_vehicle_msgs` (`colcon build`) и выполните `source install/setup.bash` в том же
> терминале.

### 6.3. Чтение без установки ROS (Python)

Метаданные (`metadata.yaml`) читаются без ROS. Для чтения самих сообщений удобна
библиотека [`rosbags`](https://pypi.org/project/rosbags/) (чистый Python, ROS ставить не
нужно):

```python
from rosbags.highlevel import AnyReader
from pathlib import Path

with AnyReader([Path('data/30618_0e41eac3')]) as reader:
    conns = [c for c in reader.connections
             if c.topic == '/vehicle/front_bogie_velocity']
    for conn, timestamp, raw in reader.messages(connections=conns):
        msg = reader.deserialize(raw, conn.msgtype)
        print(timestamp, msg.velocity)
```

Для десериализации кастомных типов зарегистрируйте `.msg`-определения из папки
`tram_vehicle_msgs/msg/` в `rosbags` через `get_types_from_msg` + `typestore.register`
(имена типов — `tram_vehicle_msgs/msg/VelocitySensor` и
`tram_vehicle_msgs/msg/DriverControllerCommand`). Стандартные типы (`NavSatFix`,
`TwistStamped`, `Odometry`) поддерживаются из коробки.

Файлы `*.db3` — это обычные базы **SQLite3**: при необходимости их можно открыть напрямую
(таблицы `topics` и `messages`), но полезная нагрузка сообщений сериализована в **CDR**,
поэтому для корректного разбора всё равно нужны определения типов.
